# 按需阅读：审查清单

> 提炼自 `dsh-code-review`。改动涉及接口、生命周期、并发、配置或公开契约时对照此清单；纯局部改动跳过。

## 必拦项（命中即 block）

- 新的或改动的文字（文档、JSDoc、注释、提示词、诊断、UI 文案）是否准确、放对地方、且覆盖了调用方需要的契约？别靠门禁自动过。
- 配置、默认值、错误码、事件、对外行为改了，包 README 和 JSDoc 在同一改动里同步了？
- 核心类型的对外描述更新了对应文档？
- 新增的注册项能干净卸载？（HMR/重载后不残留）
- 每个 invariant 都有语义上的"事件/数据关系"支撑，而不是靠服务是否存在来充数？
- 改动的每条路径都有对应证据（按表面，见 `evidence-by-surface.md`），且本地相关检查已跑？

## 人工必查

- **接口两端**：改的接口两边实现是否一致，错误、取消、所有权、资源释放是否对齐。
- **生命周期与并发**：异步初始化、回调、子进程、清理是否覆盖发布前竞态、取消时等待、独立报错、回调隔离、完整卸载到静止。
- **消费者匹配**：每个新增能力是否真有当前消费方；反过来，通用服务上新增的公开方法是否只有一个内部调用方——若是，收敛为私有闭包而不是扩 API。
- **必要性**：每个抽象、状态机、选项、兼容分支是否对应当前契约或生产消费方；无则删。
- **配置与公开选择**：每个默认值、公开操作集、格式是否有当前消费方证据或业界先例支撑；无则要求显式传参或延期决定。
- **执行点而非外观**：权限/拒绝逻辑在真正执行的那个操作上生效，而不是只在 schema/提示词/外层包装上。
- **派生状态**：所有缓存、提示、UI 回显、重放、查询视图是否在成功提交点后才更新，且源头唯一。
- **边界覆盖**：字节/条数/时间等限制在"含包装的完整结果"上生效，并测过极小、恰好、超大、跨字节边界。
- **真实入口**：测试走的是发布形态的 Loader/bin/worker/子进程路径，而非手搭的 `ctx.plugin(...)`。
- **测试力度**：用例会在预期回归上变红，且校验外部状态而非复述实现。
- **已落地决定与现状一致**：实现已交付的 Note 已改写为现在时并与代码一致。
