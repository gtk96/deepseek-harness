# 按需阅读：文档与注释自检

> 提炼自 `dsh-prose-standard` 与 `dsh-trim-cot-leakage`。改动涉及文档、注释、JSDoc、提示词或面向用户文案时对照。

## 原则

- 注释和文档只写代码表达不了的契约：行为、失败、时序、所有权、后果。别复述代码或控制流。
- 说人话，点名谁做了什么、在什么条件下、会怎样；少用"契约/边界/形态"这类抽象词，除非它指的就是那个技术主体。
- 一个事实只在一处讲透，其他地方链过去；别把同一规则抄得到处都是。
- 推理过程、计划、审查历史不进注释和文档。写完自问：这段话不看实现能独立成立吗？

## 按位置查

- **公开 JSDoc**：返回值的区分、抛错/拒绝、副作用、所有权、时序、取消、持久化。
- **内部注释**：非局部结构与"明显复杂"的局部结构——不变式、竞态顺序、所有权、安全边界、反直觉失败。
- **模块注释**：职责、依赖、非显而易见的架构选择及指向。
- **README**：消费者契约——配置、语义、失败、限制、扩展点、模型可见影响。
- **测试注释**：只解释"为何这样测"（fixture/断言/平台适配/真实入口/间接观察的必要性），不写走读。
- **提示词与可见文案**：措辞即行为，改了就要验展示或快照，或说明为何不适用。
- **诊断信息**：报清对象/路径、违反的规则、以及非显而易见时的纠正动作。

## 文风

- 保留可检索的机制名与关键的 must/may/never、时序与否定强调；装饰性加粗和感叹少用。
- 同一改动内批量套用刚学会的规则到相似段落，别只改一处。
