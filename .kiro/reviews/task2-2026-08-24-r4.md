## 发现（按严重度）

### P1 阻断

1. **真实 HTTP 响应仍未返回设计规定的 `DQ_*`。** `authorize_request` 构造了 `BusinessException(..., external_code=...)`，但 `_handle_business` 仍调用 `error(exc.biz_code, exc.msg)`；对抗输出为 `{"code":200,"bizCode":406,"msg":"denied","data":{}}`。R4 只是把字符串存进异常对象，没有完成统一响应传播。
2. **行级范围仍缺少数据集映射和权威主体生成路径。** `dq_dataset` 只有布尔 `scope_required`，没有 design 5 要求的 `scope_mapping_json`；应用层接收外部已构造的 `QuerySubject.row_scope`，未从 dic-be 权威用户资料按数据集映射生成强制过滤。布尔 fail-closed 不能证明范围值和目标维度来自权威来源。
3. **真实持久化映射无法表达 Task 2 已声明支持的维度语义。** `dq_dimension` 只有物理字段与状态，没有 `data_type/operators_json`；`_dimension_policy` 因而把所有维度默认为 `string` 和 `eq/in`。通过 ORM 加载的日期维度会在时间范围授权时被拒绝，number/date 类型及 `between/gte/lte` 也无法按治理配置使用。
4. **合法的同偏移 aware datetime 范围被错误拒绝。** `_validate_time_range` 使用对象身份 `start.tzinfo is not end.tzinfo`；`datetime.fromisoformat` 为两个 `+08:00` 端点产生不同 tzinfo 对象，对抗验证输出 `SAME_OFFSET QueryPolicyError TIME_RANGE_NOT_ALLOWED`。应区分 naive/aware 混用，并为两个 aware 值定义统一比较/归一化规则，而不是比较 tzinfo 对象身份。
5. **排序方向未在授权层闭合校验。** 运行时构造 `QueryOrderBy(direction="desc; SELECT 1--")` 后，`authorize_semantic_query` 返回授权对象；仅 Broker 二次防御拒绝。该输入应在语义授权阶段稳定分类为 `DQ_SEMANTIC_INVALID`，不能进入已授权对象后再变成编译错误。

### P2 需修

1. R4 仅新增 Broker 测试；没有为 HTTP 字符串码、同偏移 aware datetime、scope mapping、ORM 维度类型映射、指标别名排序增加应用层或真实 FastAPI 回归，导致上述缺口在 `68 passed` 下未被发现。
2. `QueryTimeRange.start/end` 仍包含 `int`，与运行时只接受 ISO 字符串不一致；治理状态、数据源、聚合、维度类型、effect、主体/资源类型仍是开放字符串。
3. `dq_access_policy` 无 `valid_from`，`_access_policy` 不映射 `expires_at`；纯领域有效期测试尚不能证明持久化应用路径满足 Requirements 4.7。
4. 数据角色 allow、未知主体、指标 deny、维度 deny 仍无专门测试。
5. 内部 HTTP Schema 仍未包含 filters/timeRange/orderBy；按 r3 约定可由后续任务补齐，但当前测试不得作为这些语义端到端可用的证据。

### P3 建议

1. 删除未使用的 `_sql_operator`，避免两套操作符映射漂移。
2. 工作树测试仍报告 `.hypothesis` 收集配置和 Starlette/httpx 共 2 个 warning；clean archive 因不含 `.hypothesis` 仅余后者，均非 Task 2 阻断。
