## 发现（按严重度）

### P1 阻断

1. **提交 `19b32bd` 不可在 clean checkout 中运行。** `git ls-files app/data_query` 仅有 service/error_code/policy/broker；service 依赖的 audit/repo、测试依赖的 assertion/models/interfaces 等仍未跟踪。`git archive HEAD` 后执行聚焦测试，在收集 `test_data_query_assertion.py` 时立即报 `ModuleNotFoundError: app.data_query.infrastructure.assertion`。当前 `66 passed` 由脏工作树未跟踪文件提供，不能作为提交证据。
2. **合法过滤、时间和强制范围维度在未被选择时无法编译。** 授权算法按要求允许独立授权过滤维度，但 `AuthorizedSemanticQuery.dimensions` 只包含 `dimension_codes`；Broker 又仅据此构造映射。对抗验证中非选择用户过滤、非选择时间维度、隐藏 scope 维度均通过授权后抛 `QueryCompilationError`。行级范围通常不应被迫加入 SELECT/GROUP BY，因此不能通过“把范围维度选出来”规避。
3. **scope fail-closed 没有进入真实应用映射。** `DatasetPolicy.scope_required` 只在纯领域对象和测试出现；`service._dataset_policy` 不读取持久化对象的该值，实测输入 `True` 输出 `False`，且 ORM/领域均没有 design 要求的 scope mapping。生产路径仍会把需要范围的数据集当作不需要范围。
4. **排序方向可注入 SQL/多语句。** `QueryOrderBy.direction` 只有 `Literal` 注解，没有运行时检查；授权只检查字段，Broker 直接 `.upper()` 拼接。对抗验证生成 `ORDER BY \`amount\` DESC; SELECT 1-- LIMIT 10`，违反 Requirements 5.4、5.6 和只读单语句安全要求。
5. **混合时区 datetime 仍泄漏裸 `TypeError`。** ISO 解析成功后，naive 与 aware datetime 在 `start < end` 比较处抛 TypeError；异常未转换为 `TIME_RANGE_NOT_ALLOWED`/`DQ_SEMANTIC_INVALID`。
6. **真实 HTTP 错误码仍不是设计规定的 `DQ_*`。** `BusinessException.biz_code` 和 `error()` 均按 int 设计，service 只选择 405/406；实测语义非法响应值为数值 `406`。新增 `ExternalErrorCode` 字符串仍未到达统一响应，不能满足 design 10.2 的跨服务稳定码。

### P2 需修

1. 指标排序映射到原始 `source_field`；对于 `SUM(amount) AS total` 会生成 `ORDER BY amount`，应按已选择指标的聚合别名或受控聚合表达式排序。
2. `QueryTimeRange.start/end` 类型注解仍包含 `int`，与运行时只接受 ISO 字符串不一致；治理状态、数据源、聚合、维度类型、effect、主体/资源类型仍是开放字符串。
3. `DATASET_NOT_PUBLISHED`/`SOURCE_NOT_ALLOWED` 的 policy/semantic 分类尚未解决资源存在性泄露疑问。
4. 内部 HTTP Schema 目前只包含 dataset/metrics/dimensions/limit；filters/timeRange/orderBy 的完整输入支持属于后续任务，但 r3 新增测试不能作为这些语义端到端可用的证据。
5. 数据角色 allow、未知主体、指标/维度 deny 仍缺少专门测试。

### P3 建议

1. `_sql_operator` 当前未使用，可删除或统一由 `_filter_sql` 使用，避免两套操作符映射漂移。
2. pytest 仍有 `.hypothesis` 收集配置和 Starlette/httpx 弃用共 2 个 warning，非任务 2 阻断。
