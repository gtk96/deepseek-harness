**结论：已解决。**

`dic-be/tests/test_data_query_execution_audit.py::test_every_execution_terminal_state_is_audited_without_payload_leakage` 当前使用文件型 `sqlite+aiosqlite`、真实 `AsyncSession`、真实 `QueryAuditLog` 表和生产 `repo.add_audit_log()`；测试只 monkeypatch 授权返回，未 mock 审计仓储。每个执行结束后都从 SQLite 执行 `select(QueryAuditLog).order_by(QueryAuditLog.id)`，再解析实体的最终 `detail_json`。

参数化集合完整覆盖：

- success；
- executor unavailable → `DQ_EXECUTOR_UNAVAILABLE`；
- timeout → `DQ_QUERY_TIMEOUT`；
- source failure → `DQ_SOURCE_FAILED`；
- source failure with unsafe jobId → `DQ_SOURCE_FAILED` 且 jobId 不持久化；
- Provider result failure → `DQ_RESULT_INVALID`；
- result projection/validation failure → `DQ_RESULT_INVALID`。

当前测试在构造 `expected_error_code = None if expected_code is None else expected_code.value` 后，显式执行：

```python
assert details[-1].get("errorCode") == expected_error_code
assert lifecycle_logs[-1].get("errorCode") == details[-1].get("errorCode")
```

因此每个失败终态同时约束了：最终持久 `detail_json.errorCode` 等于预期稳定码，以及同事件 `security_detail.errorCode` 等于持久值；success 同时约束两侧均无错误码值。测试还保持：所有持久事件和日志 `turnId == "turn-1"`；存在安全 jobId 时日志与持久值相等；unsafe jobId 不进入持久审计；应用日志事件序列与持久审计事件序列一致。单独的 compilation failure 测试同样使用真实 SQLite，断言持久 `DQ_COMPILATION_FAILED`，并通过日志对象包含同一持久 detail 完成关联。
